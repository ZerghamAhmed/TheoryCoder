Objects that play different roles in actions should have different types. This prevents the planner from making invalid substitutions.
PRESERVE the existing types from the domain file and ADD new types if needed for new objects.

TYPE COMPATIBILITY (avoid type mismatches with existing predicates):
When your new operator's precondition references an EXISTING predicate from the prior domain, the argument types you pass MUST match that predicate's declared parameter types.
If an existing predicate is declared as `(somepred ?x - typeT)` and your new operator's precondition includes `(somepred ?z)`, then `?z` must be declared as either:
  (a) `?z - typeT` directly (reusing the existing type), OR
  (b) `?z - newtype` where `newtype - typeT` is added to the :types section (declaring `newtype` as a subtype of `typeT`).
Do NOT introduce a sibling type that is unrelated to `typeT` and then pass it where `typeT` is expected — the planner will ground zero operators and produce no plan.

VARIABLES IN PRECONDITIONS AND EFFECTS (avoid hardcoded object names):
An action's :precondition and :effect may ONLY reference variables declared in that action's :parameters (the `?` symbols). Do NOT use bare object names from the problem file (like `obj_a`) inside an action's :precondition or :effect — every entity referenced must be a declared parameter. If the action needs an extra entity, ADD it to the :parameters list.
For example, this is INVALID and the planner will reject the domain:
  (:action use_tool
    :parameters (?a - agent ?t - target)
    :precondition (holding ?a tool_a)   ;; `tool_a` is not a parameter — INVALID
    :effect (used ?t))
Correct form: declare every referenced entity as a parameter, e.g. `:parameters (?a - agent ?tool - item ?t - target)` and reference `?tool` in the precondition.
